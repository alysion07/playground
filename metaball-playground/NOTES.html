§0 3~4시간 플랜

§1 30초 요약

뭘 하는 토이? 여러 블롭(원)이 서로 붙어 녹듯 합쳐지는 2D 화면.

어떻게? 각 블롭을 원의 SDF로 표현 → smooth-min으로 합산 → 화면 전체를 덮는 프래그먼트 셰이더 한 장이 픽셀마다 직접 색 계산.

왜 이 기법? 메시 변형으로 "녹는 경계"를 그리려면 지옥. SDF는 거리 함수 하나로 합집합·AA·rim·bloom을 전부 처리.

§2 데이터 흐름 (한 프레임)

  1. CPUappStore가 blob 배열 보관 (pos, radius, color).
  2. CPUphysics.step이 position-Verlet으로 좌표 갱신. 중력·인력·포인터·경계.
  3. CPUloop.ts가 blob 값을 uniforms에 복사 (uBlobsXYZR, uColors, 그리고 uK·uAA 등).
  4. GPU풀스크린 삼각형 1개 드로우콜. 버텍스는 좌표만 통과.
  5. GPU프래그먼트 셰이더가 픽셀마다: d = smin(d, sdCircle(p, b.xy, b.z), k)을 블롭 개수만큼.
  6. GPUmask = 1 - smoothstep(0, aa, d) + 거리 기반 rim/bloom + vignette → 픽셀 색.

매 프레임 1~6을 반복. 블롭 개수만큼 픽셀당 루프 — fragment 비용이 O(N).

§3 3대 개념

SDF (Signed Distance Field)

점 p에서 가장 가까운 표면까지의 부호 있는 거리 d(p).

  • 표면 = d=0, 안쪽 = 음수, 바깥 = 양수
  • 원 SDF: sdCircle(p, c, r) = |p - c| - r
  • 여러 SDF의 min = 합집합 (union)
  • 거리 함수 하나로 합성·AA·rim·shadow 모두 가능
SDF = 점 p에서 가장 가까운 표면까지의 부호 있는 거리. 등고선 = 같은 거리의 궤적.
Smooth-min (polynomial) 
h = max(k - |a - b|, 0) / k
smin(a, b, k) = min(a, b) - h² · k · 0.25
  • k = 0이면 순수 min (경계 꺾임)
  • k가 클수록 두 SDF가 k만큼 떨어져 있을 때부터 섞이기 시작 → "더 멀리서부터 끈적하게 붙음"
  • 감소량 h²·k/4 ≤ k/4 — 원래 min보다 살짝만 더 작게 빠져 SDF 성질 유지
  • 이 코드의 uK = 0.001 + blobSmoothness × 0.5 (world units)
회색 = min (두 SDF 하단 envelope · 꺾임) · 파랑 = smin (경계가 안쪽으로 녹음 → "붙는" 효과)
Full-screen triangle + fragment-only
  • 삼각형 1개로 [-1, 3]² 영역을 덮고 NDC [-1, 1]²만 scissor
  • 쿼드(삼각형 2개)보다 대각선 경계에서 overdraw·이음새 없음
  • 버텍스 셰이더는 단순 통과만 — 실제 그림은 fragment shader 혼자
  • depthTest: false, depthWrite: false (깊이 없음)
파랑 삼각형 1개가 노랑 NDC를 완전히 덮음 · 쿼드의 대각선 이음새 없음

§4 현재 코드가 아직 안 하는 것

오해 주의
  • Raymarching 아님 — 2D 화면 공간이라 픽셀 당 d(p) 한 번이면 끝. 3D sphere tracing은 Week 2+ 로드맵.
  • WebGPU 미사용 — metaball.wgsl은 Week 2 포팅 참조용. 지금은 renderer.ts에서 backend: 'webgl2' 고정, 실제 셰이더는 metaball.glsl.
  • 진짜 3D normal 계산 없음 — rim/bloom은 d 기반 근사. ∇d를 유한차분으로 구해 normal 뽑는 건 3D 토이에서 등장.

§6 셰이더 섹션 포인터

Phase 2: metaball.glsl을 위→아래로. 각 덩어리에서 스스로 던질 질문.

1~22줄 · uniform 블록
  • MAX_BLOBS가 #ifndef로 주입됨 — material.ts의 defines에서 넘어옴
  • uniform vec4 uBlobsXYZR[MAX_BLOBS]에서 xy = pos, z = radius, w = unused
  • Q: 왜 vec3 배열 + 별도 radius uniform 대신 vec4로? (힌트: std140 padding)
23~31줄 · sdCircle + smin
  • sdCircle은 벡터 2개 빼고 길이 재고 r 빼면 끝 — 3줄
  • smin은 §3의 polynomial 공식 그대로
  • Q: k <= 0 예외 처리가 왜 필요? (0으로 나누기 방지 + 순수 min 유지)
33~36줄 · NDC → world p
  • vNdc는 [-1, 1]. 거기에 aspect와 0.5를 곱해 world 좌표로
  • Q: aspect를 x에만 곱하는 이유? (세로 기준 정사각 단위 만들기)
38~51줄 · 블롭 합성 루프
  • for (int i = 0; i < MAX_BLOBS; i++) if (i >= count) break; 패턴
  • Q: 왜 i < count로 안 하고 이렇게? (GLSL의 uniform array 루프는 상수 bound 요구 — 옛 관행)
  • 색은 exp(-max(d_i, 0) · softness) 가중치로 합산 → 가까운 블롭이 지배
53~77줄 · mask / rim / bloom / vignette
  • inside = 1 - smoothstep(0, aaWorld, d) — AA 적용된 내부 마스크
  • rim: exp(-(d/aaWorld·6)²) — d가 0 근처(경계)일 때만 밝음. 3D rim이 아님
  • bloom: exp(-max(d,0)·scale) — 경계 바깥으로 발광 근사
  • vignette: NDC 길이 기반 어두워짐

Q: store 변경이 즉시 GPU에 반영되나? → 아니다. 다음 프레임 loop가 읽어 복사할 때 반영.

physics.ts — position-Verlet
  • velocity를 따로 저장 안 함 → v ≈ (pos - prev) / h
  • 업데이트: new_pos = pos + (pos - prev) · damp + a · h²
  • 서브스텝: 최대 3회, FIXED_DT = 1/120으로 쪼갬
  • Q: 왜 Verlet? → 에너지 보존이 Euler보다 우월. 드롭 프레임에도 튀지 않음.
material.ts — uniform 계약
  • TS Vector4 ↔ GLSL vec4 — three가 알아서 매핑
  • uBlobsXYZR 배열은 MAX_BLOBS 길이로 미리 할당 → 런타임엔 덮어쓰기만
  • MAX_BLOBS는 defines로 GLSL에 주입 (컴파일 타임 상수)

§8 플래시카드 (Q 탭 → A)

먼저 본인 머릿속에서 2~4문장으로 답 → 탭해서 확인.

SDF가 뭔가요? 왜 블롭에 자연스러운 선택인가요? L1
점 p에서 가장 가까운 표면까지의 부호 있는 거리 d(p). 표면 d=0, 안쪽 음수, 바깥 양수. 여러 SDF의 min이 합집합이고, smooth-min으로 바꾸면 경계가 녹아 "붙는" 효과가 됨 — 블롭의 본질. 메시 변형보다 연산·합성·AA 모두 거리 함수 하나로 처리.
풀스크린 삼각형 1개가 쿼드(삼각형 2개)보다 좋은 점? L1
쿼드는 대각선에서 래스터라이저가 두 삼각형 경계 픽셀을 중복 shading해 overdraw·미세 이음새 가능. 삼각형 1개([-1,-1],[3,-1],[-1,3])는 NDC [-1,1]²을 완전히 덮고 scissor만 → 경계선 자체가 없음. GPU 파이프라인 관점에서 더 빠르고 깔끔.
smin과 min의 차이? k의 의미? L1
min은 두 SDF 교차에서 경계가 꺾여 날카로운 union. smin은 h = max(k-|a-b|, 0)/k, min(a,b) - h²k/4로 근방에서 부드럽게 함몰. k = smoothness (world units); 0이면 순수 min, 커질수록 두 SDF가 k만큼 떨어져 있을 때부터 섞이기 시작 → "더 멀리서 끈적하게".
블롭 N개 화면 W×H일 때 프레임당 sdCircle 호출 수는? L2
픽셀마다 for가 N회 → W × H × N. 1920×1080, N=10이면 ~2천만 회/프레임. GPU가 병렬이라 실시간이지만 픽셀당 O(N)이라 블롭 수가 fragment 비용에 직결.
uBlobsXYZR는 vec4인데 w는 어디 쓰나? 왜 낭비처럼 해둔 것 같나? L2
현재 w는 unused. std140 UBO 레이아웃에서 vec3 배열은 원소마다 16바이트로 패딩됨 — 어차피 vec4 공간을 먹음. 그래서 명시적 vec4로 쓰고 w는 미래 확장 슬롯(예: blob 타입 플래그, fade 값)으로 보존. 메모리 낭비 아님.
이 코드의 rim/bloom은 3D 모델의 rim/bloom과 뭐가 다른가? L2
3D rim은 surface normal과 view 벡터의 dot으로 엣지 판정. 여기엔 normal도 view도 없고 오직 SDF d값. exp(-(d/aaWorld·6)²)로 d가 0 근처(경계 근방)일 때만 밝아지도록 근사. bloom도 post-process blur 아닌 exp(-max(d,0)·scale)로 경계 바깥 발광 근사. 전부 거리 기반 가짜 효과.
블롭 10 → 100개일 때 병목은? 어떻게 확인? L3
픽셀당 O(N) 루프니 fragment-bound 가능성이 가장 큼. uniform 업로드는 vec4×100 = 400 floats/프레임으로 무시 수준. 확인법: dpr을 1.5 → 0.5로 낮춰 렌더 픽셀을 감소시키고 프레임타임이 선형으로 회복되면 fragment 확정. 브라우저 GPU 프로파일러(Perf → GPU)로도 확인 가능.
WebGL2 → WebGPU 전환 시 셰이더 두 파일 동기화 전략? L3
런타임 GLSL→WGSL 번역은 기능·정밀도 차이 때문에 비현실적. 작은 프로젝트는 수동 동기화 + CPU 참조 구현 테스트 (이 repo의 util/smin.ts)로 두 경로를 같은 값에 맞춤. 규모 커지면 SDF 조합을 AST/JSON 중간표현으로 두고 언어별 템플릿에 주입 (erosion-sculptor의 sdfGen.ts가 그 방향).
